# Fase 3.1 — Stack tecnológico y versiones

## 1. Cómo leer este documento

Las versiones de abajo son la **línea base propuesta**, fijada según el estado del ecosistema
conocido al redactar el plan. Antes de escribir la primera línea de código, la tarea `T-A-01`
verifica y congela las versiones reales:

```bash
npm view electron dist-tags
npm view electron versions --json | tail -20
node --version
```

El resultado se registra en `/proyecto/gestion/bitacora.md` y **sustituye** esta tabla. Es
deliberado: un plan que fija versiones sin verificarlas envejece mal, y uno que no las fija no es
ejecutable. La verificación es una tarea, no una omisión.

**Todas las versiones se fijan exactas** en `package.json` (sin `^` ni `~`) y se acompañan de
`package-lock.json` versionado. En una aplicación que produce evidencia contable, una construcción
reproducible no es opcional.

## 2. Tiempo de ejecución y framework

| Componente | Versión base | Justificación |
|---|---|---|
| **Node.js (herramientas)** | LTS activa (24.x; mínimo 22.x) | Solo para construir. El Node que ejecuta la app es el que Electron incorpora |
| **Electron** | La major estable más reciente con soporte activo. **Mínimo absoluto: 33.x** | Electron mantiene las 3 últimas majors. Por debajo de 33 se pierden parches de seguridad de Chromium. El mínimo 33 garantiza `utilityProcess` maduro, `safeStorage`, y un Chromium moderno |
| **Chromium (renderer)** | El que traiga Electron | No se elige por separado. Determina el `build.target` de Vite para el renderer |

### Política de versión de Electron (`ADR-002`)

1. Se fija **exacta** al iniciar el proyecto.
2. Se revisa cada 8 semanas (cadencia de Electron). Actualizar dentro de la misma major es
   obligatorio si hay parche de seguridad.
3. Cambiar de major exige: recompilar los módulos nativos, ejecutar la suite E2E completa y generar
   los instaladores. No se hace en la semana previa a una entrega.
4. **Nunca** bajar de la versión mínima soportada por el proyecto.

### Relación Electron ↔ frontend (punto 5 del encargo)

La versión de Electron determina el Chromium del renderer, y ese Chromium es **conocido y único** en
el escritorio. Eso permite dos configuraciones de compilación distintas, que es exactamente lo que
se hace en [3.2 Compatibilidad](3.2_compatibilidad.md):

- **Renderer de escritorio:** objetivo `chrome<N>` de la versión de Electron. Sin transpilación
  innecesaria: menos código, menos *polyfills*, mejor rendimiento.
- **Código compartido y web-desplegable:** objetivo del piso de 4 años (`R-05`). Más conservador.

## 8. Lo que se descarta explícitamente

Para que nadie lo reabra:

| Descartado | Motivo |
|---|---|
| **Prisma** | Su motor de consulta es un binario que complica el empaquetado en Electron y multiplica el tamaño del instalador |
| **Tailwind CSS v4** | Rompe el piso de compatibilidad `R-05` (`RG-09`) |
| **Electron Forge** | electron-vite + electron-builder da mejor experiencia de desarrollo y más control del empaquetado. Forge es una alternativa válida, no superior aquí |
| **Redux Toolkit** | Sobrado para el caso: el estado de servidor lo lleva TanStack Query y el de interfaz es pequeño |
| **Jest** | Fricción con ESM y con la configuración de Vite. Vitest reutiliza la misma configuración |
| **Spectron** | Discontinuado. Playwright es la vía soportada |
| **`node:sqlite`** | Aún experimental y atado a la versión de Node que traiga Electron. `better-sqlite3` está probado en producción |
| **Un servidor HTTP interno para el renderer** | Rompe `R-02` y abre superficie de ataque. Solo el módulo LAN de v1.5, si se autoriza |
| **Material UI / Ant Design** | Peso, opiniones visuales fuertes y difícil de ajustar a la densidad que exige un listado de 20.000 filas |

| Elemento | Objetivo |

| Aplicación instalada | < 350 MB |

dos commits requiere justificación.
