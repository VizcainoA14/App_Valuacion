# Fase 6 — Estrategia de pruebas

## 1. Principio de asignación de esfuerzo

No se busca una cobertura uniforme. Se busca **cobertura proporcional a la consecuencia del error**.

| Componente | Consecuencia de un fallo | Cobertura objetivo | Tipo dominante |
|---|---|:-:|---|
| **Motor de cálculo** (`MOD-06`) | Estados financieros de una entidad pública mal ajustados; resoluciones firmadas sobre cifras erróneas | **100 % de ramas** | Unitaria + propiedad |
| Importador / normalizador | Datos inventados en silencio | ≥ 95 % | Unitaria + archivos reales |
| Reglas de integridad (`INT-*`) | Evidencia contractual alterable | **100 %** | Integración por SQL directo |
| Máquinas de estado | Bajas o actos fuera de procedimiento | **100 %** | Unitaria |
| Casos de uso | Transacción a medias, bitácora perdida | ≥ 80 % | Integración |
| Adaptador IPC | Superficie de ataque | ≥ 90 % | Integración |
| Componentes de interfaz | Molestia | ≥ 60 % | Componente |
| Pantallas | Molestia | flujos críticos | E2E |

Una cobertura del 100% en el motor y del 60% en los diálogos es la asignación correcta, no una
inconsistencia.

## 2. Pirámide

```
              ┌──────────────┐
              │   E2E  ~25   │  Playwright + Electron, sobre el paquete construido
              ├──────────────┤
              │ Integración  │  ~150  · casos de uso con SQLite en memoria + IPC + triggers
              │              │
              ├──────────────┤
              │  Componente  │  ~120  · Testing Library, por comportamiento
              ├──────────────┤

              └──────────────┘
```

## 3. Nivel 1 — Unitarias (Vitest)

### 3.1 Motor de cálculo: el conjunto que no puede fallar

| Grupo | Contenido | Origen |
|---|---|:-:|
| Casos mínimos | Los 15 de `ANEXO_C` §11 | `T-D-01` |
| Casos recalculados | Los ejemplos de §2.3 y §3.3, con las cifras que las fórmulas producen (CT-01) | `T-D-01` |
| Casos borde | Cada fila de §2.4, §3.4 y §5.5 | `T-D-01` |
| Métodos de conteo | Los tres de §3.3, con el mismo bien, comparados | `T-B-02` |
| Redondeo | `RED-01` … `RED-06` | `T-B-02` |
| Propiedades | P1…P8 con `fast-check` | `T-D-01` |
| Golden test | Contra el archivo de cálculo real del hospital | `T-D-02` |

**Regla de disciplina (mitigación de `RG-01`):** ningún valor esperado del motor se modifica sin una
entrada en `/proyecto/gestion/bitacora.md` que explique por qué. Un test que se ajusta al código
deja de ser una prueba.

### 3.2 Pruebas de propiedad

`fast-check` genera miles de entradas válidas y comprueba invariantes que deben cumplirse siempre:

```ts
test('P1 — la depreciación acumulada nunca supera la base depreciable', () => {
  fc.assert(fc.property(arbBienCalculable(), arbParametros(), (bien, params) => {
    const r = calcularDepreciacion(bien, params);
    if (r.estado !== 'CALCULADO') return true;
    return r.valor.depreciacionAcumuladaCent <= r.valor.baseDepreciableCent;
  }));
});
```

Encuentran lo que los casos de ejemplo no: fechas de 29 de febrero, vidas útiles de un mes, costos
en el límite del entero seguro, bienes adquiridos exactamente en la fecha de corte.

### 3.3 Normalizadores

Cada regla de `ANEXO_C` §9 tiene su prueba, con los valores sucios que `ANEXO_A` §3.4 documenta como
frecuentes en datos reales:

```
"NO REGISTRA", "NT", "N/A", "-", ""     → null, nunca 0
"$ 1.788.720"                            → 178872000 centavos
"19/07/2019"                             → "2019-07-19", con el formato detectado reportado
45107 (serial de Excel)                  → "2023-06-15"
"2023-13-45"                             → rechazo, no adivinar
"  EQUIPO   DE  RAYOS X "                → "EQUIPO DE RAYOS X"
"bueno"                                  → "BUENO" (validado contra el catálogo)
```

## 4. Nivel 2 — Componente (Testing Library)

Se prueba **comportamiento observable**, no implementación:

| Prueba | Verifica |
|---|---|
| `<CampoSensible>` no deja guardar sin justificación | `ANEXO_B` §7.1 |
| `<TablaDatos>` con 20.000 filas renderiza solo las visibles | `RNF-01` |

| El importador muestra los errores por fila antes de confirmar | `T-C-07` |

## 5. Nivel 3 — Integración

Casos de uso reales contra **SQLite en memoria** con el esquema completo y los triggers activos. Sin
simulacros de la base: se prueba contra el motor real, porque una parte importante de las reglas
(`INT-*`) vive en él.

Pruebas que solo existen en este nivel:

| Prueba | Verifica |
|---|---|
| Violar cada `INT-*` **por SQL directo** | Que la integridad no depende de la aplicación |
| Escribir en un ejercicio `CERRADO` por SQL directo | `INT-09`, `RNF-06` |
| Un caso de uso que falla a mitad no deja datos parciales | Atomicidad |
| La bitácora se escribe en la misma transacción que el cambio | `RNF-07` |
| Un documento generado cita al `Responsable` correcto y queda en bitácora | `T-B-07` |
| La cadena completa de migraciones sobre una base de la versión anterior | `RG-11` |
| Importar los **20 `.xlsx` reales** | `RG-04`, CT-07 |
| Cuadre en tres niveles con 20.000 bienes: diferencia exactamente $0 | `RNF-03`, `RG-02` |

## 6. Nivel 4 — E2E (Playwright + Electron)

Sobre el **paquete construido**, no sobre el servidor de desarrollo: es la única forma de probar lo
que el usuario recibirá.

```ts
import { _electron as electron } from 'playwright';
const app = await electron.launch({ args: ['out/main/index.js'] });
const ventana = await app.firstWindow();
```

Flujos cubiertos (~25 escenarios):

| # | Flujo | Requisitos |
|:-:|---|---|
| 1 | Crear entidad → parametrizar → abrir ejercicio | Paso 01 completo |
| 2 | Importar `PL-02b` con errores → ver informe → corregir → importar | `RG-04` |
| 3 | Editar un bien importado; rechazo de código o placa duplicados | `RN-02-01` |
| 4 | Importar `PL-03` de 2.000 filas | `RF-02-07` |
| 5 | Completar hojas de vida; un bien sin costo queda `INCOMPLETO` | `RN-03-01` |
| 6 | Importar saldos → emparejar → clasificar partidas → cuadrar | Paso 04 |
| 7 | Calcular obsolescencia; verificar semáforos e índice > 1 sin truncar | Paso 05 |
| 8 | Calcular depreciación con los tres métodos; comparar | Paso 06 |
| 9 | Valuar; intentar guardar sin justificación → rechazado | `VAL-07-02` |
| 10 | Cargar inmueble y avalúo; lista de chequeo bloqueante | Paso 08 |
| 11 | Proponer baja → Comité aprueba → resolución | Paso 09 |
| 12 | Consolidar → cuadre falla → resoluciones bloqueadas | `RN-10-02` |

telemetría en una aplicación que se instala en hospitales con la red restringida.

## 7. Datos de prueba

`scripts/sembrar.ts` genera ejercicios sintéticos deterministas (semilla fija):

| Conjunto | Bienes | Uso |
|---|:-:|---|
| `minimo` | 20 | Pruebas rápidas, desarrollo |
| `tipico` | 2.000 | Hospital de baja complejidad |
| `carga` | 20.000 | Límite superior de `ANEXO_B` §9 |
| `sucio` | 500 | Con los defectos reales: fechas mezcladas, `NO REGISTRA`, costos en cero, series duplicadas, bienes de terceros |

El conjunto `sucio` es el más valioso: reproduce lo que `00_MARCO_GENERAL` §10 advierte que va a
llegar.

**Datos reales:** si el cliente entrega archivos de un hospital, se anonimizan antes de incorporarlos
a `tests/fixtures/` (nombres de responsables, números de factura, proveedores). Nunca se versionan
datos identificables de una entidad.

## 8. Lo que no se prueba automáticamente

Se declara para que se cubra a mano y quede constancia:

| Área | Cómo se verifica |
|---|---|
| Fidelidad visual del PDF impreso | Revisión manual con lista de chequeo por informe |
| Lectura de etiquetas con el escáner físico | Prueba manual con el equipo real (`T-G-06`) |
| Instalación en máquina limpia | Máquina virtual limpia por cada versión (`T-A-03`, `T-H-01`) |
| Usabilidad de la captura en campo | Sesión con un técnico real |
| Corrección contable de las fórmulas | **Revisión del contador de la entidad.** Ninguna prueba automática sustituye esto |

La última fila es la más importante del documento: el motor puede pasar 500 pruebas y seguir
implementando una interpretación equivocada de una regla contable. Por eso `T-D-02` (golden test
contra el archivo real) y la firma del acta `EN-06-04` son parte del plan.
