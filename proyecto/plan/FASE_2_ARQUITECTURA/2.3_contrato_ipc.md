# Fase 2.3 — Contrato IPC

## 1. Principio

> "Validate all IPC message data in the main process since the renderer is untrusted like a browser."
> — `.claude/skills/electron-skill/SKILL.md`

El contrato IPC es **el único punto de entrada al dominio**. Todo lo que cruza esa frontera se
valida, se autoriza y se registra. No hay atajos.

## 2. Forma del contrato

Un único archivo en `MOD-00` declara, por canal: el esquema Zod de entrada, el tipo de salida y el
permiso requerido. Main, preload y renderer derivan de ahí; no hay tres definiciones que puedan
desincronizarse.

```ts
// src/compartido/ipc/contrato.ts
export const contrato = {

  'ejercicio:crear': {
    entrada: z.object({
      entidadId: uuid,
      nombre: z.string().trim().min(3).max(150),
      fechaCorte: fechaIso,                       // no futura: se valida en el dominio
      contratoNumero: z.string().max(50).optional(),
    }),
    salida: z.custom<EjercicioDto>(),
    permiso: 'ejercicio.crear',
    muta: true,
  },

  'bien:listar': {
    entrada: z.object({
      ejercicioId: uuid,
      filtros: filtrosBienSchema.optional(),
      orden: ordenSchema.optional(),
      pagina: z.number().int().min(0).default(0),
      tamano: z.number().int().min(1).max(1000).default(200),
    }),
    salida: z.custom<Pagina<BienListadoDto>>(),
    permiso: 'bien.leer',
    muta: false,
  },

  'depreciacion:calcularEjercicio': {
    entrada: z.object({ ejercicioId: uuid }),
    salida: z.custom<ResumenCalculoDto>(),
    permiso: 'calculo.ejecutar',
    muta: true,
    larga: true,        // emite progreso y admite cancelación
  },

} as const;

export type Contrato = typeof contrato;
export const CANALES = Object.keys(contrato) as (keyof Contrato)[];
```

## 3. Convención de nombres

`<modulo>:<accion>` en `lowerCamelCase` para la acción. Verbo primero.

| Patrón | Ejemplos |
|---|---|
| Lectura | `bien:listar`, `bien:porId`, `ejercicio:listar`, `conciliacion:matriz` |
| Escritura | `bien:crear`, `bien:actualizar`, `bien:trasladar`, `baja:proponer` |
| Proceso largo | `depreciacion:calcularEjercicio`, `importacion:ejecutar`, `expediente:compilar` |
| Documento | `documento:generarResolucion`, `documento:exportarExcel`, `documento:imprimirPdf` |
| Eventos main → renderer | `evento:progreso`, `evento:calculoFinalizado`, `evento:alerta` |

Prohibido un canal genérico tipo `db:query` o `app:ejecutar`: reabre toda la superficie de ataque
que el aislamiento cierra.

## 4. Middleware del main (orden fijo)

Cada `ipcMain.handle` pasa por la misma cadena, generada automáticamente desde el contrato:

```
 1. ¿El canal existe en el contrato?                    → si no: error, y se registra
 2. Validar la entrada con Zod                          → si falla: ErrorValidacion con detalle de campo
 3. (sin resolución de sesión: la app no tiene inicio de sesión — ADR-016)
 4. (sin comprobación de permisos: la app no tiene usuarios — ADR-016)
 5. Si `muta`: comprobar que el ejercicio no esté CERRADO  (INT-09)
 6. Ejecutar el caso de uso
 7. Si `muta`: escribir bitácora dentro de la misma transacción
 8. Serializar la salida (structured clone)             → sin funciones, sin Date crudas
 9. Capturar y traducir errores de dominio a DTO de error
```

Los pasos 1 a 5 y 7 a 9 son **infraestructura común**: se escriben una vez (`T-B-08`). El
desarrollador que añade un canal escribe solo el paso 6.

## 5. Serialización: reglas que evitan errores silenciosos

El IPC de Electron usa el algoritmo de clonación estructurada. Consecuencias prácticas:

| Tipo | Cómo cruza | Motivo |
|---|---|---|
| **Dinero** | `string` decimal canónico (`"23739280.00"`) o `number` de centavos, nunca `number` de pesos | `RG-02`. El renderer solo formatea; no opera |
| **Fechas** | `string` ISO `AAAA-MM-DD` (fecha) o ISO 8601 completo (marca de tiempo) | `Date` cruza, pero arrastra la zona horaria del proceso. Las fechas de corte son **fechas sin hora**; convertirlas a `Date` introduce desfases de un día |
| **Índices y factores** | `number` con 4 decimales | No se suman; el flotante es aceptable (`RED-03`) |
| **Enums** | `string` de la unión literal de `MOD-00` | Único origen de verdad |
| **Errores** | DTO `{ tipo, codigo, mensaje, campo?, detalle? }` | Un `Error` de JS pierde su clase al cruzar |
| **Buffers (PDF, Excel)** | `Uint8Array`, o mejor: se escribe en el almacén y se devuelve la ruta | Un `.xlsx` de 20.000 filas por IPC es memoria duplicada |

> La regla de la fecha es la que más errores previene. Todo el motor de cálculo depende de
> `fecha_corte`; un desfase de zona horaria de una hora convierte `2025-06-30` en `2025-06-29` y
> cambia la depreciación de miles de bienes. **Las fechas de negocio son cadenas `AAAA-MM-DD` en
> todo el sistema, incluida la base de datos.**

## 6. Operaciones largas: progreso y cancelación

Los canales marcados `larga: true` siguen un protocolo único:

```
renderer                         main
   │ invoke('depreciacion:calcularEjercicio', {ejercicioId})
   │                              │ genera tareaId, responde inmediato { tareaId }
   │ ←──────────────────────────  │
   │ suscribe 'evento:progreso'   │ webContents.send('evento:progreso',
   │ ←──────────────────────────  │   { tareaId, hechos, total, fase })
   │                              │
   │ invoke('tarea:cancelar', {tareaId})   → marca la bandera; el lote actual termina y para
   │ ←── 'evento:tareaFinalizada' { tareaId, estado: 'ok'|'cancelada'|'error', resumen }
```

Reglas:
- El progreso se emite **como máximo cada 250 ms**; emitir por registro satura el IPC y ralentiza
  más que el propio cálculo.
- Cancelar **no revierte** lo ya persistido; deja el cálculo en estado `PARCIAL` y lo declara así.
  Un cálculo parcial nunca se presenta como completo (`RG-07`).
- El renderer se desuscribe siempre en el retorno de `useEffect`.

## 7. Cliente tipado en el renderer

```ts
// src/renderer/ipc/cliente.ts
export const api = crearCliente<Contrato>(window.api);

// uso, con inferencia completa de tipos:
const pagina = await api['bien:listar']({ ejercicioId, pagina: 0, tamano: 200 });
```

Integrado con TanStack Query, cada canal de lectura se convierte en una clave de caché
(`['bien:listar', entrada]`) y cada canal de escritura declara qué claves invalida. Ver
[2.5](2.5_estado_renderer.md).

## 8. Prohibiciones explícitas

| # | Prohibido | Por qué |
|:-:|---|---|
| P-1 | Un canal que reciba una ruta de archivo arbitraria del renderer y la lea o escriba | Escape del sandbox por *path traversal*. El renderer solo envía identificadores; el main resuelve rutas dentro del almacén |
| P-2 | Un canal que reciba SQL, un fragmento de SQL o un nombre de tabla | Inyección |
| P-3 | Un canal que reciba código, expresiones o plantillas para evaluar | Ejecución remota |
| P-4 | Reenviar al renderer una excepción con su traza | Filtra rutas del sistema y estructura interna |
| P-5 | `ipcRenderer.sendSync` | Bloquea el renderer |
| P-6 | Emitir eventos a **todas** las ventanas cuando solo una los pidió | Fugas de datos entre ventanas |

Sobre P-1: cuando el usuario elige un archivo, el diálogo lo abre el **main**
(`dialog.showOpenDialog`), no el renderer. El main obtiene la ruta directamente del sistema
operativo; nunca la recibe del código no confiable.

## 9. Verificación

| Comprobación | Cómo |
|---|---|
| Todo canal registrado está en el contrato, y viceversa | Test que compara `CANALES` con los `ipcMain.handle` registrados (`T-B-08`) |
| Todo canal declara permiso | Type-level: el contrato lo exige |
| Ninguna entrada llega sin validar | El registro de handlers es la **única** forma de crear un canal; no se llama `ipcMain.handle` directamente |
| El preload no expone nada más | Test que enumera las claves de `window.api` |
