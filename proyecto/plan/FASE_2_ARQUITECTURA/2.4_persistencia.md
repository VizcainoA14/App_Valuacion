# Fase 2.4 — Persistencia

## 1. Motor

**SQLite**, un archivo por instalación, vía `better-sqlite3` (ver
[ADR-004](../DECISIONES/adr_stack.md#adr-004--motor-de-persistencia)).

```
PRAGMA journal_mode = WAL;          -- lectura concurrente durante escritura
PRAGMA foreign_keys = ON;           -- SQLite las desactiva por defecto: crítico
PRAGMA busy_timeout = 5000;
PRAGMA synchronous = NORMAL;        -- con WAL es seguro y mucho más rápido
PRAGMA temp_store = MEMORY;
```

`foreign_keys = ON` debe ejecutarse **en cada conexión**, no una vez en el archivo. Es un error
clásico: las claves foráneas se declaran, no se aplican, y las inconsistencias aparecen meses
después.

## 2. Convenciones del esquema

| Aspecto | Convención | Motivo |
|---|---|---|
| Nombres | `snake_case`, tablas en singular, igual que `ANEXO_B` | Trazabilidad directa con `/especificacion/teoria` |
| Claves primarias | `TEXT` con UUID v7 | UUID v7 es ordenable por tiempo: índices sanos, sin la fragmentación de v4 |
| **Dinero** | `INTEGER` de **centavos** | `SUM()` exacto de 64 bits; `RG-02`, `RNF-03` |
| **Índices y factores** | `INTEGER` escalado ×10.000 | `RED-03`: 4 decimales exactos y reproducibles |
| **Fechas de negocio** | `TEXT` `AAAA-MM-DD` | Comparables lexicográficamente, sin zona horaria |
| **Marcas de tiempo** | `TEXT` ISO 8601 UTC | Auditoría |
| Booleanos | `INTEGER` 0/1 con `CHECK (col IN (0,1))` | SQLite no tiene booleano |
| Enums | `TEXT` con `CHECK (col IN (...))` | Los 15 enums de `ANEXO_B` §5, generados desde `MOD-00` |
| Nulos | Se distingue `NULL` (dato no disponible) de `0` | `RN-03-02`, `ANEXO_A` §3.4. **Es una regla de negocio, no un detalle** |

### Sufijos que hacen legible el tipo

```
costo_adquisicion_cent      INTEGER   -- centavos
indice_obsolescencia_x10k   INTEGER   -- ×10.000
fecha_corte                 TEXT      -- AAAA-MM-DD
calculado_en                TEXT      -- ISO 8601 UTC
```

La capa de repositorio traduce a los nombres de `/especificacion/teoria` en los DTO. La base es explícita; la API
es legible.

## 3. Índices obligatorios

De `ANEXO_B` §3, más los derivados de las consultas reales:

```sql
CREATE UNIQUE INDEX ux_bien_codigo  ON bien(ejercicio_id, codigo_institucional);  -- INT-01
CREATE UNIQUE INDEX ux_bien_placa   ON bien(ejercicio_id, placa);                 -- INT-01
CREATE INDEX ix_bien_clase          ON bien(ejercicio_id, clase_activo_id);
CREATE INDEX ix_bien_servicio       ON bien(ejercicio_id, servicio_id);
CREATE INDEX ix_bien_serie          ON bien(serie);                    -- VAL-02-07
CREATE INDEX ix_bien_estado         ON bien(ejercicio_id, estado_registro);
CREATE INDEX ix_calc_dep_ejercicio  ON calculo_depreciacion(ejercicio_id, bien_id);
CREATE INDEX ix_calc_obs_ejercicio  ON calculo_obsolescencia(ejercicio_id, bien_id);
CREATE INDEX ix_bitacora_registro   ON bitacora(entidad_afectada, registro_id);
CREATE INDEX ix_bitacora_ejercicio  ON bitacora(ejercicio_id, fecha);
```

Para la búsqueda por descripción del listado de bienes (30 pantallas de listado lo usan) se añade
una tabla virtual **FTS5** sobre `descripcion_funcional`, `marca`, `modelo`, `serie`, sincronizada
por triggers. Sin ella, buscar en 20.000 filas obliga a `LIKE '%...%'` sin índice.

## 4. Reglas de integridad en la base, no solo en la aplicación

Las 10 reglas `INT-01` … `INT-10` de `ANEXO_B` §8 se implementan **en el motor**, donde ningún
código puede saltárselas:

| Regla | Implementación |
|---|---|
| `INT-01` únicos por ejercicio | Índices únicos (arriba) |
| `INT-02` un bien no cambia de ejercicio | Trigger `BEFORE UPDATE ... WHEN NEW.ejercicio_id <> OLD.ejercicio_id → RAISE(ABORT)` |
| `INT-03` no borrar bien con cálculos | `ON DELETE RESTRICT` + trigger que prohíbe `DELETE` sobre `bien`, siempre |
| `INT-04` `fecha_adquisicion ≤ fecha_corte` | `CHECK` no puede consultar otra tabla → trigger `BEFORE INSERT/UPDATE` sobre `hoja_vida` |
| `INT-05` `depreciacion_acumulada ≤ base_depreciable` | `CHECK (depreciacion_acumulada_cent <= base_depreciable_cent)` en la misma fila |
| `INT-06` `valor_avaluo_final ≥ 0` | `CHECK (valor_avaluo_final_cent >= 0)` |
| `INT-07` baja `EJECUTADO` exige `acta_comite_id` | Trigger de transición de estado |
| `INT-08` acto firmado exige `acta_comite_id` | Trigger de transición de estado |
| `INT-09` **ejercicio `CERRADO` rechaza toda escritura** | Ver §6 |
| `INT-10` clase no depreciable sin cálculo de depreciación | Trigger `BEFORE INSERT` sobre `calculo_depreciacion` |

> **Por qué en la base:** un ejercicio cerrado es evidencia contractual y puede ser objeto de
> auditoría. Si la única defensa está en TypeScript, basta un script, una migración mal escrita o un
> `INSERT` desde una herramienta externa para alterarla sin dejar rastro.

## 5. Enum canónico de `estado_registro` (resuelve CT-06)

```
BORRADOR ──→ VALIDADO ──→ ACTIVO ──→ PROPUESTO_BAJA ──→ DADO_DE_BAJA
    │            │           ▲              │
    └────────────┴──→ INCOMPLETO ───────────┘
                         ▲   │       (rechazo del Comité, RN-09-04)
                         └───┘        PROPUESTO_BAJA ──→ ACTIVO
```

| Desde | Hacia | Condición |
|---|---|---|
| `BORRADOR` | `VALIDADO` | Pasa `VAL-02-01`…`VAL-02-04` |
| `VALIDADO` | `ACTIVO` | Tiene hoja de vida si su clase la requiere (`VAL-03-01`) |
| cualquiera | `INCOMPLETO` | Falta `fecha_adquisicion` o `costo_adquisicion` (`RN-03-01`) |
| `INCOMPLETO` | `ACTIVO` | Se completó el dato económico |
| `ACTIVO` | `PROPUESTO_BAJA` | Existe `PropuestaBaja` (paso 09) |
| `PROPUESTO_BAJA` | `ACTIVO` | Comité rechaza (`RN-09-04`) |
| `PROPUESTO_BAJA` | `DADO_DE_BAJA` | Acta del Comité aprueba (`INT-07`) |
| `DADO_DE_BAJA` | — | **Terminal.** El bien nunca se elimina (`RN-09-09`) |

La tabla de transiciones vive en `MOD-00` como dato, no como `if`s, y la usan tanto el dominio como
el trigger generado.

## 6. Inmutabilidad del ejercicio cerrado

Dos capas, ver [ADR-017](../DECISIONES/adr_arquitectura.md#adr-017--inmutabilidad-del-ejercicio-cerrado):

1. **Triggers.** Cada tabla con `ejercicio_id` lleva tres triggers (`INSERT`, `UPDATE`, `DELETE`)
   que consultan el estado del ejercicio y llaman a `RAISE(ABORT, 'INT-09: ejercicio cerrado')`. Se
   generan por script a partir de la lista de tablas; no se escriben a mano.
2. **Sello de integridad.** Al cerrar, se calcula un SHA-256 sobre una serialización canónica y
   ordenada del contenido del ejercicio y se guarda en `cierre_ejercicio.hash_contenido`, junto con
   fecha, usuario y versión de la aplicación. La app puede reverificarlo en cualquier momento y
   demostrar que el ejercicio no fue alterado. Un instrumento de auditoría, no de seguridad.

## 7. Migraciones

```
src/main/infraestructura/db/migraciones/
├── 0001_esquema_inicial.sql
├── 0002_indices_fts.sql
├── 0003_triggers_inmutabilidad.sql
└── ...
```

- Numeradas, **solo hacia adelante**, nunca editadas después de publicarse.
- Versión rastreada con `PRAGMA user_version`.
- **Respaldo automático verificado antes de cada migración** (`RG-11`): se copia el archivo, se abre
  la copia, se ejecuta `PRAGMA integrity_check` y solo entonces se migra.
- Si la base tiene una versión **mayor** que la aplicación (el usuario instaló una versión anterior),
  la app se niega a abrirla y lo explica. Nunca "intentar y ver".
- CI ejecuta la cadena completa de migraciones sobre una base sembrada de la versión anterior
  (`T-A-08`).

## 8. Respaldos

| Cuándo | Retención |
|---|---|
| Antes de cada migración | Permanente hasta confirmación manual |
| Al cerrar un ejercicio | **Permanente** — es evidencia contractual |
| Antes de una importación masiva | Últimos 5 |
| Diario, al primer arranque del día | Últimos 10, rotativo |
| Bajo demanda del usuario | El usuario elige destino |

Todo respaldo se hace con la API `db.backup()` de SQLite (consistente con WAL activo), **nunca**
copiando el archivo con el sistema de archivos mientras hay conexiones abiertas.

## 9. Exportación e importación de ejercicio (`.valz`)

Sustituye la sincronización móvil de `RF-02-01` (CT-05 / ADR-015) y sirve además para respaldo y
para entrega al cliente.

```
ejercicio.valz  (ZIP)
├── manifiesto.json        versión de la app, del esquema, entidad, ejercicio, fecha, hash
├── datos.db               SQLite con solo ese ejercicio y sus catálogos
├── almacen/               adjuntos y fotos referenciados
└── firma.txt              SHA-256 del contenido
```

La importación es **fusión con reporte de conflictos**, nunca sobrescritura silenciosa: por cada
registro coincidente muestra ambas versiones y el usuario decide. Los conflictos se resuelven por
`codigo_institucional` + `placa` (`INT-01`), no por marca de tiempo — la resolución automática por
tiempo que sugiere `ANEXO_B` §9 es inaceptable cuando el dato en disputa es el costo de un activo.

## 10. Volumen y rendimiento esperados

| Magnitud | Estimación | Consecuencia |
|---|---|---|
| Bienes por ejercicio | 800 – 20.000 (`ANEXO_B` §9) | Trivial para SQLite |
| Filas de cálculo por ejercicio | 2 × bienes (obsolescencia + depreciación) | ≤ 40.000 |
| Bitácora | ~10 filas por bien a lo largo del ejercicio | ~200.000 filas; indexada, sin problema |
| Tamaño de la base sin adjuntos | < 200 MB | — |
| Adjuntos y fotos | 1–3 fotos por bien, ~200 KB comprimidas | Hasta ~12 GB — **fuera de la base**, en el almacén (CT-14) |

Presupuesto de rendimiento (`RNF-02`): listar 200 bienes con filtros, **< 50 ms**; calcular 20.000
bienes, **< 15 s**; cuadre de todas las subcuentas, **< 1 s**. Se mide en `T-D-06` con datos
sintéticos generados por `scripts/sembrar.ts`.
