# Fase 2.1 — Arquitectura general

## 1. Estilo arquitectónico

**Monolito modular con núcleo hexagonal.** Un solo ejecutable, una sola base de datos local, un solo
ciclo de despliegue (restricción `R-02`), pero internamente dividido en módulos de dominio con
fronteras verificadas por herramienta (ver [1.2](../FASE_1_ANALISIS/1.2_modulos_y_dominios.md) §4).

No es microservicios disfrazados ni un monolito de una sola pieza: es **un monolito cuyas costuras
están dibujadas donde el negocio las tiene**.

## 2. Las cuatro capas

```
┌──────────────────────────────────────────────────────────────────────┐
│  PRESENTACIÓN  ·  proceso renderer  ·  React 19                      │
│  Pantallas, tablas, formularios, gráficas. Sin lógica de negocio.    │
│  Habla exclusivamente por el cliente IPC tipado.                     │
└─────────────────────────────┬────────────────────────────────────────┘
                              │  window.api.<modulo>.<metodo>()   (preload)
┌─────────────────────────────▼────────────────────────────────────────┐
│  ADAPTADOR IPC  ·  proceso main                                      │
│  Un handler por canal. Valida la entrada con Zod. Resuelve el        │
│  usuario y el permiso. Traduce errores de dominio a errores IPC.     │
│  NO contiene reglas de negocio.                                      │
└─────────────────────────────┬────────────────────────────────────────┘
                              │
┌─────────────────────────────▼────────────────────────────────────────┐
│  APLICACIÓN  ·  casos de uso  ·  proceso main                        │
│  Orquesta: abre transacción, lee repositorios, invoca el dominio,    │
│  persiste, escribe bitácora, emite eventos de progreso.              │
│  Un caso de uso = una intención del usuario = una transacción.       │
└──────────┬──────────────────────────────────────┬────────────────────┘
           │                                      │
┌──────────▼─────────────────┐    ┌───────────────▼────────────────────┐
│  DOMINIO  (MOD-06 y otros) │    │  INFRAESTRUCTURA (adaptadores)     │
│  Motor de cálculo, reglas, │    │  SQLite, sistema de archivos,      │
│  máquinas de estado,       │    │  ExcelJS, docxtemplater, printToPDF │
│  validaciones, invariantes │    │  Implementan los puertos.          │
│  PURO: sin IO, sin Node,   │    │                                    │
│  sin Electron, sin React   │    │                                    │
└────────────────────────────┘    └────────────────────────────────────┘
```

**La regla de dependencia apunta siempre hacia adentro.** El dominio no conoce a nadie. La
infraestructura implementa interfaces (*puertos*) que el dominio y la aplicación declaran.

## 3. Anatomía de un caso de uso

Ejemplo real, `calcularDepreciacionEjercicio` (paso 06):

```ts
// src/main/modules/depreciacion/casos-uso/calcularDepreciacionEjercicio.ts
export async function calcularDepreciacionEjercicio(
  deps: { db: BaseDatos; bitacora: Bitacora; progreso: EmisorProgreso },
  entrada: { ejercicioId: Uuid; usuarioId: Uuid },
): Promise<ResultadoCalculo> {

  // 1. Precondiciones de estado — invariantes, no reglas de negocio
  const ejercicio = await deps.db.ejercicios.porId(entrada.ejercicioId);
  assertEjercicioEditable(ejercicio);                    // INT-09

  // 2. Parámetros CONGELADOS del ejercicio, no los vigentes  (RN-01-01)
  const parametros = ParametrosCalculo.desdeSnapshot(ejercicio.parametrosCongelados);

  // 3. Validaciones bloqueantes del paso            (VAL-06-01 … VAL-06-06)
  const val = validarPaso06(ejercicio, parametros);
  if (val.tieneBloqueantes) return ResultadoCalculo.bloqueado(val);

  // 4. Lectura por lotes  → objeto de entrada aplanado          (CT-10)
  //    Bien + HojaVida + ClaseActivo → EntradaCalculoBien
  // 5. DOMINIO PURO: la única línea que calcula.  Sin IO.
  //      motorDepreciacion.calcular(entrada, parametros)
  // 6. Persistencia transaccional por lotes de 500
  // 7. Bitácora: acción CALCULAR, con método aplicado
  // 8. Emisión de progreso hacia el renderer
}
```

Puntos no negociables de este esqueleto:

| # | Regla | Motivo |
|:-:|---|---|
| 1 | Los parámetros vienen del **snapshot congelado**, nunca del catálogo vigente | `RN-01-01`: reproducibilidad. Un cambio de catálogo no puede alterar un ejercicio abierto |
| 2 | La verificación de ejercicio editable es lo **primero** | `INT-09` |
| 3 | El cálculo ocurre en una función pura que recibe datos y devuelve datos | Testeable sin base de datos; ejecuta los 15 casos de `ANEXO_C` §11 en milisegundos |
| 4 | Una transacción por caso de uso; si falla, no queda nada a medias | Un cálculo parcial produce un balance descuadrado |
| 5 | La bitácora se escribe **dentro** de la misma transacción | Si el cambio persiste, su rastro también. `RNF-07` |

## 4. Puertos declarados por el dominio y la aplicación

| Puerto | Implementación v1 | Sustituible por |
|---|---|---|
| `RepositorioBienes`, `RepositorioEjercicios`, … | SQLite / Drizzle | Cualquier motor SQL |
| `AlmacenArchivos` | Sistema de archivos en `userData` | Almacenamiento de objetos, si algún día hay servidor |
| `LectorLibroExcel` / `EscritorLibroExcel` | ExcelJS | SheetJS |
| `GeneradorDocumento` (Word) | docxtemplater | Cualquier motor de plantillas |
| `GeneradorPdf` | `webContents.printToPDF` | Puppeteer, wkhtmltopdf |
| `GeneradorCodigoBarras` | bwip-js | JsBarcode + qrcode |
| `Reloj` | `Date` del sistema | Reloj fijo en tests — **imprescindible**: todo el cálculo depende de fechas |
| `Bitacora` | Tabla SQLite + decorador | — |

> El puerto `Reloj` no es un lujo: sin él, ningún test sobre `fecha_corte` es reproducible y los
> casos de `ANEXO_C` §11 fallarían al cambiar el día.

## 5. Modelo de errores

Errores tipados, nunca cadenas de texto. Tres familias, que el adaptador IPC traduce a códigos que
el renderer sabe presentar:

| Familia | Ejemplo | Presentación en la UI |
|---|---|---|
| `ErrorValidacion` | `VAL-06-03` incumplida | Panel de validaciones del paso, con el código citado |
| `ErrorReglaNegocio` | intento de escribir en ejercicio `CERRADO` (`INT-09`) | Diálogo explicativo, no un "error inesperado" |
| `ErrorNoCalculable` | falta `costo_adquisicion` (`RN-03-01`) | **No es un error**: el bien va a la bandeja de incompletos |

La tercera familia es la que más se olvida y la que `/especificacion/teoria` más subraya:
`ANEXO_C` §2.4 y §3.4 distinguen `NoCalculable` de `Error`. Un bien sin costo **no rompe** el
cálculo del ejercicio; se excluye, se cuenta y se reporta (`RN-06-05`, `VAL-06-09`).

## 6. Concurrencia y transacciones

- Un único escritor: el proceso main. El renderer nunca toca la base.
- SQLite en modo **WAL**, `busy_timeout` configurado, para que el `utilityProcess` de cálculo pueda
  leer mientras el main escribe.
- Las operaciones masivas (importación, cálculo) se hacen en lotes de 500 dentro de transacciones,
  con emisión de progreso entre lotes.
- **No hay concurrencia entre usuarios** (ver CT-08 / ADR-016). Si se abre una segunda instancia de
  la aplicación sobre la misma base, se detecta con `app.requestSingleInstanceLock()` y se enfoca la
  ventana existente en lugar de abrir otra.

## 7. Ciclo de vida de un ejercicio (invariante central del sistema)

```
   crear ejercicio                        cerrar ejercicio
        │  congela parámetros                   │  calcula hash SHA-256 del contenido
        │  (RN-01-01)                           │  activa triggers de solo lectura
        ▼                                       ▼
   ABIERTO → EN_LEVANTAMIENTO → EN_CONCILIACION → EN_CALCULO
           → EN_VALUACION → EN_APROBACION → CERRADO  (terminal, inmutable)
```

Todo el sistema gira alrededor de este objeto:

- **Todo dato transaccional cuelga de un `ejercicio_id`.** Los catálogos (entidad, sedes, clases)
  no; por eso se congelan al abrir.
- Un `Bien` **no puede cambiar de ejercicio** (`INT-02`).
- Un ejercicio `CERRADO` rechaza toda escritura (`INT-09`), a nivel de base de datos, no solo de
  aplicación (ver [ADR-017](../DECISIONES/adr_arquitectura.md#adr-017--inmutabilidad-del-ejercicio-cerrado)).
- El siguiente corte abre un ejercicio nuevo que **hereda los bienes y recalcula** (`RF-11-08`).

## 8. Qué NO hace esta arquitectura

Declarado explícitamente para que nadie lo intente:

- **No hay servidor.** Ni HTTP, ni GraphQL, ni base de datos remota (salvo el módulo LAN opcional de
  v1.5, que sería un componente aislado y autorizado por separado).
- **No hay ORM con motor externo.** Prisma queda descartado por su binario de consulta, difícil de
  empaquetar en Electron (ADR-005).
- **No hay estado global de negocio en el renderer.** El renderer cachea respuestas de IPC; la
  verdad vive en SQLite.
- **No hay lógica de cálculo en SQL.** Las fórmulas de `ANEXO_C` viven en TypeScript puro y
  testeable. SQL solo agrega y filtra. La única excepción autorizada son las sumas de control del
  cuadre (`SUM()` sobre enteros de centavos), precisamente porque SQLite las hace exactas.
