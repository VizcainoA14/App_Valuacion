# Fase 4.3 — Configuración y variables de entorno

## 1. Principio: tres niveles de configuración, sin mezclarlos

`/especificacion/teoria/README.md` §4 establece que **nada está quemado en el código**. Pero "parámetro" significa
tres cosas distintas y confundirlas produce un sistema imposible de mantener:

| Nivel | Qué es | Dónde vive | Quién lo cambia | Ejemplo |
|---|---|---|---|---|
| **1. Entorno de construcción** | Cómo se compila y empaqueta | `.env`, variables de CI | Desarrollador | `PERFIL=web`, `ELECTRON_MIRROR` |
| **2. Preferencias de instalación** | Cómo se comporta esta copia instalada | `userData/config.json` | Administrador local | Ruta de datos, tema, densidad, idioma de fecha |
| **3. Parámetros de negocio** | Reglas de cálculo y catálogos de la entidad | **Base de datos** (`ParametroCalculo`, `ClaseActivo`, …) | El operador, con registro en bitácora | `metodo_conteo_meses`, vidas útiles, umbrales |

**El nivel 3 nunca es una variable de entorno.** Es dato de negocio, se versiona, se congela por
ejercicio (`RN-01-01`) y cada cambio queda en bitácora. Poner `UMBRAL_SEMAFORO_VERDE=0.5` en un
`.env` destruiría la trazabilidad que `/especificacion/teoria` exige.

## 2. Nivel 1 — Variables de entorno de construcción

`.env.example` (versionado; `.env` no):

```bash
# ── Perfil de compilación ────────────────────────────────────────────
# electron (por defecto) | web
# Determina el objetivo de esbuild. Ver plan FASE_3/3.2.
PERFIL=electron

# ── Desarrollo ───────────────────────────────────────────────────────
# Ruta alterna del directorio de datos, para no tocar la instalación real
VITE_DEV_DATOS=

# Abre las herramientas de desarrollo al arrancar
VITE_DEV_TOOLS=false

# Nivel de registro: error | warn | info | debug
LOG_NIVEL=info

# ── Empaquetado (solo CI, nunca en local) ────────────────────────────
# Firma de código Windows. Ver ADR-024 y RG-18.
CSC_LINK=
CSC_KEY_PASSWORD=

# Espejo de descarga de binarios de Electron, si la red del cliente lo exige
ELECTRON_MIRROR=
```

Reglas:

| # | Regla |
|:-:|---|
| E-1 | `.env` **no se versiona**. `.env.example` sí, con todas las claves y sin valores |
| E-2 | Solo las variables con prefijo `VITE_` llegan al renderer. El resto se queda en el proceso de construcción |
| E-3 | **Ninguna variable contiene un secreto de producción**: la aplicación no habla con servicios externos (`RNF-08`). Las únicas credenciales posibles son las de firma de código, y viven en el gestor de secretos de CI |
| E-4 | Si una variable falta, la aplicación **no arranca con un valor inventado**: falla con un mensaje claro. Los valores por defecto se declaran en un único módulo `src/main/config/entorno.ts`, validado con Zod al arrancar |

## 3. Nivel 2 — Configuración de la instalación

`userData/config.json`. Se lee **antes** de abrir la base de datos, por lo que no puede vivir en
ella.

```jsonc
{
  "version": 1,
  "rutaDatos": null,            // null = userData por defecto; ver validación abajo
  "tema": "sistema",            // claro | oscuro | sistema
  "densidad": "comoda",         // compacta | comoda
  "idiomaFecha": "es-CO",
  "respaldos": {
    "diario": true,
    "retencionDias": 30,
    "rutaExterna": null         // por ejemplo, una carpeta de respaldo institucional
  },
  "importacion": {
    "formatoFechaRegional": "DD/MM/AAAA"   // ANEXO_C §9.1: resuelve la ambigüedad DD vs MM
  },
  "ultimoEjercicioAbierto": null,
  "ventana": { "ancho": 1440, "alto": 900, "maximizada": false }
}
```

### Validación de `rutaDatos` (mitiga `RG-10`)

Al arrancar, si `rutaDatos` apunta a una ruta UNC (`\\servidor\...`) o a una unidad mapeada de red,
la aplicación **se niega a abrir la base** y muestra un diálogo explicativo:

> La base de datos no puede residir en una unidad de red. SQLite se corrompe con el bloqueo de
> archivos por red, y este sistema custodia evidencia contable. Use una ruta local y configure un
> respaldo automático hacia la carpeta institucional.

La detección se hace con `GetDriveType` en Windows y comprobando el tipo de sistema de archivos en
Linux y macOS. **No es una advertencia que se pueda ignorar**: es un bloqueo. Perder un ejercicio
cerrado por corrupción no tiene remedio.

`respaldos.rutaExterna` existe precisamente para atender la necesidad legítima que hay detrás
("queremos que esté en el servidor"): la base es local y los respaldos se copian a la red.

## 4. Nivel 3 — Parámetros de negocio

Viven en la base, en `ParametroCalculo`, `ClaseActivo`, `ConvencionCodigo`, `AbreviaturaTipo` y
`FactorEstado`. Reglas de `/especificacion/teoria` que el código debe respetar:

| Regla | Implicación técnica |
|---|---|
| `RN-01-01` los parámetros se congelan por ejercicio | Al crear un ejercicio se serializa el conjunto completo en `Ejercicio.parametros_congelados` (JSON). **El motor lee de ahí, nunca del catálogo vigente** |
| `RN-01-06` una sola fecha de corte por ejercicio | Cambiarla dispara recálculo total y entrada en bitácora |
| `VAL-01-07` el método de conteo debe estar **confirmado** | El valor sugerido es `dias_exactos`, pero la aplicación bloquea el cálculo hasta la confirmación explícita por acta (CT-02) |
| `ANEXO_D` §1 el listado normativo es configurable por entidad y ejercicio | Tabla `NormaAplicable(entidad_id, ejercicio_id, norma, materia)`. **Ninguna norma escrita en el código** |
| `ANEXO_A` §4.2 las plantillas documentales son editables y versionadas | `userData/plantillas/<version>/`, con la versión usada registrada en cada ejercicio |

### Semillas de arranque

`recursos/semillas/` contiene sugerencias editables, no constantes:

```
clases_sugeridas.json     catálogo de clases de activo típico de una E.S.E (RF-01-03)
abreviaturas.json         abreviaturas por tipo de bien para el plaqueteo (RN-01-02)
subcuentas.json           subcuentas del Catálogo General de Cuentas (Res. 139/2015)
normas.json               marco normativo de ANEXO_D §2, con su fecha de verificación
parametros_defecto.json   valores por defecto de ANEXO_B §2.5
hospital_demo.json        hospital de demostración completo (T-B-11)
```

Se **copian** a la base al crear la entidad y desde ese momento pertenecen a la entidad. Actualizar
la aplicación no altera los catálogos de un hospital ya configurado.

`normas.json` incluye una fecha de verificación por norma, porque `ANEXO_D` §1 advierte
expresamente que el marco normativo cambia con frecuencia y debe comprobarse antes de citarlo en un
acto administrativo. La aplicación muestra esa fecha al insertar una norma en una resolución.

---

### Hospital de demostración (`T-B-11`)

`hospital_demo.json` contiene una entidad ficticia completa —2 sedes, 8 servicios, 6 clases, 50
bienes con hoja de vida, 1 inmueble con avalúo y 1 ejercicio con fecha de corte— que el usuario puede
cargar y borrar cuando quiera.

Tres salvaguardas obligatorias:

| # | Salvaguarda |
|:-:|---|
| 1 | Bandera `es_demostracion` en la entidad, y **banda visible permanente** en la interfaz mientras esté activa |
| 2 | Borrado de un clic, que elimina la entidad y todo lo suyo sin tocar datos reales |
| 3 | Todo documento generado desde la demostración lleva marca de agua **"EJEMPLO — SIN VALIDEZ"** |

La tercera importa más de lo que parece: una resolución de prueba sin distintivo, circulando por
correo en un hospital, es un problema real.

## 5. Registro de eventos (logging)

| Aspecto | Decisión |
|---|---|
| Destino | `userData/logs/app-AAAA-MM-DD.log`, rotación de 14 días |
| Niveles | `error`, `warn`, `info`, `debug` (configurable con `LOG_NIVEL`) |
| Qué **sí** se registra | Arranque, versión, migraciones, respaldos, importaciones (archivo, filas, rechazos), ejecuciones de cálculo (duración, excluidos), errores de IPC |
| Qué **nunca** se registra | Contraseñas, contenido de campos económicos, datos personales de responsables de custodia |
| Relación con la bitácora | Son cosas distintas. El **log** es técnico y se borra. La **bitácora** (`ANEXO_B` §7.1) es evidencia de auditoría, vive en la base y **nunca** se borra |

Esa última distinción se explicita porque confundirlas lleva a purgar evidencia contable creyendo
que se limpian archivos temporales.

---

## 6. Precedencia de configuración

```
1. Argumento de línea de comandos   (--datos=<ruta>, --log=debug)
2. Variable de entorno              (solo nivel 1)
3. userData/config.json             (nivel 2)
4. Valores por defecto del código   (declarados en un solo módulo, validados con Zod)
```

Los parámetros de negocio (nivel 3) **no participan de esta cadena**: solo vienen de la base y, para
un ejercicio, solo del snapshot congelado.
