# Hito A — Esqueleto ejecutable

**Tareas:** `T-A-01` … `T-A-08` (ver [backlog](5.0_backlog_maestro.md))
**Se puede empezar:** ahora. No depende de ninguna decisión pendiente del cliente.

## Objetivo

Una aplicación Electron que arranca, abre SQLite, **se empaqueta en un instalador y se instala en
una máquina limpia**, con CI verde. Sin una sola regla de negocio.

## Por qué este hito existe y va primero

Todo el riesgo técnico *no funcional* del proyecto vive aquí:

| Riesgo | Cuándo aparece si no se hace el hito A | Coste |
|---|---|---|
| `RG-06` módulo nativo roto en el empaquetado | Al preparar la primera entrega | Días perdidos en la peor semana posible |
| `RG-09` una librería rompe el piso `R-05` | Cuando ya hay 40 pantallas escritas con ella | Reescritura del sistema visual |
| `RG-17` versión de Electron sin soporte | A mitad del proyecto | Migración de major bajo presión |
| Fronteras entre módulos no verificadas | Nunca — simplemente se degradan | La modularidad se pierde en silencio |

Empaquetar el día uno con una aplicación de 20 líneas cuesta unas horas. Empaquetar el día ciento
veinte con 40.000 líneas cuesta una semana y ocurre justo antes de una entrega.

## Notas de ejecución

### `T-A-01` — Congelar versiones

No es burocracia: este plan propone una línea base (`FASE_3/3.1`) que debe **verificarse contra el
registro real de npm** antes de instalar nada. El resultado —Electron, su Chromium, su Node, y las
versiones de React y TypeScript— se escribe en `app/docs/decisiones-runtime.md` y en
`/proyecto/gestion/bitacora.md`. A partir de ahí, esas son las versiones del proyecto.

También aquí se ejecuta `npx update-browserslist-db@latest`: una base de datos de navegadores vieja
produce un `.browserslistrc` que miente sin avisar.

### `T-A-03` — El instalador, antes que la lógica

Criterio de aceptación estricto: el `.exe` se instala en una **máquina limpia** (o una máquina
virtual sin herramientas de desarrollo) y la aplicación abre y ejecuta `SELECT 1` contra SQLite.
Probarlo en la máquina de desarrollo no vale: ahí están las herramientas de compilación de Node que
el usuario final no tendrá.

Puntos concretos que hay que dejar resueltos:

```yaml
# electron-builder.yml
asarUnpack:
  - "**/node_modules/better-sqlite3/**"     # el .node debe quedar fuera del asar
files:
  - "!**/*.map"
```

y `postinstall: electron-builder install-app-deps` en `package.json`.

### `T-A-04` — Las reglas antes que el código que deben gobernar

Configurar `dependency-cruiser` y `eslint-plugin-compat` **antes** de escribir módulos. Una regla de
frontera añadida después de tener 200 archivos solo sirve para producir 300 errores que nadie
arregla. Añadida antes, impide que se creen.

La prueba de que funciona: escribir a propósito un `import 'fs'` dentro de `src/compartido/motor/` y
comprobar que la construcción falla; luego borrarlo.

### `T-A-06` — Trazabilidad automática desde el principio

`scripts/trazabilidad.ts` recorre `/especificacion/teoria`, extrae con expresiones regulares todos los códigos
`RF-`, `RN-`, `VAL-`, `EN-`, `INT-` y produce `docs/trazabilidad.csv` con estado `PENDIENTE`. A
partir de ese momento existe una lista objetiva de lo que falta, y CI detecta si `/especificacion/teoria` cambia
(`RG-15`).

## Definición de terminado del hito

- [ ] Versiones congeladas y registradas en `docs/decisiones-runtime.md`.
- [ ] `npm run dev` abre una ventana con recarga en caliente del renderer.
- [ ] Instalador generado, **instalado en máquina limpia**, abre y consulta SQLite.
- [ ] Las reglas de frontera (D-1…D-6) y el piso `R-05` fallan la construcción cuando se violan.
- [ ] Test de configuración segura de `BrowserWindow` en verde.
- [ ] `docs/trazabilidad.csv` generado con los ~331 requisitos en estado `PENDIENTE`.
- [ ] CI en verde en Windows y Linux, incluyendo empaquetado y E2E sobre el paquete.
- [ ] Medición base de tamaño y arranque registrada.
- [ ] **Cero reglas de negocio implementadas.** Si hay alguna, se sacó de sitio.
