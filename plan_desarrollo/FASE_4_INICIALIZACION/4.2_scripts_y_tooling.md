# Fase 4.2 — Scripts, herramientas y flujo de trabajo

## 1. Scripts de `package.json`

```jsonc
{
  "scripts": {
    // ── Desarrollo ────────────────────────────────────────────────
    "dev":              "electron-vite dev",
    "dev:watch":        "electron-vite dev --watch",

    // ── Construcción ──────────────────────────────────────────────
    "typecheck":        "tsc -b --noEmit",
    "build":            "npm run typecheck && electron-vite build",
    "build:web":        "PERFIL=web electron-vite build",   // perfil de piso R-05

    // ── Empaquetado ───────────────────────────────────────────────
    "pack":             "npm run build && electron-builder --dir",
    "dist:win":         "npm run build && electron-builder --win --publish never",
    "dist:mac":         "npm run build && electron-builder --mac --publish never",
    "dist:linux":       "npm run build && electron-builder --linux --publish never",

    // ── Calidad ───────────────────────────────────────────────────
    "lint":             "eslint . && stylelint \"src/**/*.css\"",
    "lint:fix":         "eslint . --fix && stylelint \"src/**/*.css\" --fix",
    "format":           "prettier --write .",
    "boundaries":       "depcruise src --config .dependency-cruiser.js",
    "compat":           "npx browserslist && eslint src/renderer src/compartido --rule '{\"compat/compat\":\"error\"}'",

    // ── Pruebas ───────────────────────────────────────────────────
    "test":             "vitest run",
    "test:watch":       "vitest",
    "test:motor":       "vitest run src/compartido/motor",   // rápido, el que más se ejecuta
    "test:cov":         "vitest run --coverage",
    "test:e2e":         "playwright test",
    "test:e2e:ui":      "playwright test --ui",

    // ── Base de datos ─────────────────────────────────────────────
    "db:generar":       "drizzle-kit generate",
    "db:migrar":        "tsx scripts/migrar.ts",
    "db:sembrar":       "tsx scripts/sembrar.ts --bienes=2000",
    "db:sembrar:carga": "tsx scripts/sembrar.ts --bienes=20000",
    "db:triggers":      "tsx scripts/generar-triggers.ts",

    // ── Proyecto ──────────────────────────────────────────────────
    "trazabilidad":     "tsx scripts/trazabilidad.ts",
    "verificar:versiones": "tsx scripts/verificar-versiones.ts",
    "verificar:todo":   "npm run typecheck && npm run lint && npm run boundaries && npm run test && npm run trazabilidad",

    "postinstall":      "electron-builder install-app-deps"
  }
}
```

`postinstall` con `install-app-deps` recompila `better-sqlite3` contra los encabezados de Electron.
Sin él, la app falla al arrancar con `The module was compiled against a different Node.js version`.
Es la causa número uno de la pérdida de la primera tarde de un proyecto Electron (`RG-06`).

`verificar:todo` es la puerta única: es lo que ejecuta CI y lo que debe pasar antes de cerrar
cualquier tarea del backlog.

## 2. Configuración de ESLint (fragmentos que importan)

```js
// eslint.config.js — configuración plana de ESLint 9
export default [
  // 1. El motor de cálculo no importa de ningún sitio impuro
  {
    files: ['src/compartido/motor/**/*.ts'],
    rules: {
      'no-restricted-imports': ['error', {
        patterns: [
          { group: ['@main/*', '@renderer/*', 'electron', 'fs', 'path', 'better-sqlite3'],
            message: 'M-1: el motor de cálculo debe ser puro. Ver plan FASE_2/2.6.' },
        ],
      }],
      'no-restricted-globals': ['error',
        { name: 'Date', message: 'M-6: la fecha entra como dato. Usa el puerto Reloj.' }],
    },
  },

  // 2. Prohibido operar dinero con number
  {
    files: ['src/**/*.ts'],
    rules: {
      'no-restricted-syntax': ['error', {
        selector: "BinaryExpression[operator=/[*/+-]/] > Identifier[name=/[Cc]ent$|Costo|Valor|Saldo/]",
        message: 'RG-02: usa decimal.js o las funciones de motor/dinero.ts. Nunca aritmética nativa sobre dinero.',
      }],
    },
  },

  // 3. Piso de compatibilidad R-05
  {
    files: ['src/renderer/**/*.{ts,tsx}', 'src/compartido/**/*.ts'],
    plugins: { compat },
    rules: { 'compat/compat': 'error' },
  },

  // 4. El renderer no toca Node
  {
    files: ['src/renderer/**/*.{ts,tsx}'],
    rules: {
      'no-restricted-imports': ['error', {
        paths: [
          { name: 'electron', message: 'El renderer solo habla por window.api.' },
          { name: 'fs' }, { name: 'path' }, { name: 'better-sqlite3' },
        ],
      }],
    },
  },
];
```

La regla 2 es heurística y producirá algún falso positivo; se acepta. El coste de un
`// eslint-disable` ocasional y justificado es mucho menor que el de un error de punto flotante en
un balance (`RG-02`).

## 3. Fronteras entre módulos

`.dependency-cruiser.js` codifica las reglas D-1 a D-6 de
[1.2 §4](../FASE_1_ANALISIS/1.2_modulos_y_dominios.md):

```js
forbidden: [
  { name: 'motor-puro',
    from: { path: '^src/compartido/motor' },
    to:   { pathNot: '^src/compartido/(motor|tipos|enums|errores)' },
    severity: 'error' },

  { name: 'compartido-no-depende-de-nadie',
    from: { path: '^src/compartido' },
    to:   { path: '^src/(main|renderer|preload)' },
    severity: 'error' },

  { name: 'renderer-no-toca-main',
    from: { path: '^src/renderer' },
    to:   { path: '^src/main' },
    severity: 'error' },

  { name: 'sin-imports-profundos-entre-modulos',
    from: { path: '^src/main/modules/([^/]+)/' },
    to:   { path: '^src/main/modules/(?!$1)([^/]+)/.+', pathNot: 'index\\.ts$' },
    severity: 'error' },
]
```

La última regla es la que sostiene la modularidad en el tiempo: obliga a pasar por el `index.ts` de
cada módulo y hace visible cualquier acoplamiento nuevo.

## 4. Ganchos de Git

```jsonc
// lint-staged
{
  "*.{ts,tsx}": ["eslint --fix", "prettier --write"],
  "*.css":      ["stylelint --fix", "prettier --write"],
  "*.{json,md,yml}": ["prettier --write"]
}
```

- **pre-commit:** `lint-staged` + `npm run test:motor` (rápido; el motor es lo que no puede romperse
  nunca sin que alguien se entere).
- **pre-push:** `npm run verificar:todo`.

## 5. Integración continua

```yaml
# .github/workflows/ci.yml  (o el equivalente del proveedor que use el cliente)
jobs:
  verificar:
    strategy: { matrix: { os: [windows-latest, ubuntu-latest] } }
    steps:
      - checkout
      - setup-node (LTS, cache npm)
      - npm ci
      - npm run typecheck
      - npm run lint
      - npm run boundaries
      - npm run compat            # ← verifica el piso R-05
      - npm run test:cov
      - npm run trazabilidad      # ← falla si /Teoria y la matriz divergen (RG-15)
      - npm run pack              # ← empaqueta en cada commit (RG-06)
      - npm run test:e2e          # ← sobre el paquete real, no sobre el servidor de desarrollo
      - npm audit --audit-level=high
```

Dos decisiones sobre CI que se toman ahora y no después:

1. **Se empaqueta en cada commit**, no solo en las publicaciones. Los fallos de módulo nativo y de
   `asarUnpack` solo aparecen en el paquete; descubrirlos tres meses después es carísimo (`RG-06`).
2. **E2E corre sobre el paquete construido**, no sobre `electron-vite dev`. Es la única forma de
   probar lo que el usuario recibirá.

Windows es la plataforma principal (parque hospitalario colombiano). Linux se incluye por ser barato
y detectar dependencias de rutas con barra invertida.

## 6. Variables de entorno de desarrollo

Ver [4.3](4.3_configuracion_y_entorno.md). En resumen: `.env` **no se versiona**, `.env.example` sí,
y ninguna variable de entorno contiene secretos de producción — la aplicación no habla con ningún
servicio externo (`RNF-08`).

## 7. Flujo de trabajo con Git

| Aspecto | Convención |
|---|---|
| Rama principal | `main`, siempre desplegable |
| Ramas de trabajo | `tarea/T-B-04-motor-parametros` — el identificador del backlog en el nombre |
| Mensajes de commit | Convencionales, con el código de tarea: `feat(motor): T-D-01 casos de ANEXO_C §11` |
| Etiquetas | `v0.1.0-hito-A`, `v0.2.0-hito-B`… una por hito cerrado |
| Requisito para fusionar | `verificar:todo` en verde + matriz de trazabilidad actualizada + entrada en `/gestion_proyecto/bitacora.md` |

> **`.gitignore` — advertencia.** El `.gitignore` actual del repositorio ignora `.claude/`
> completo. Eso excluye del control de versiones las skills y el archivo de configuración de sesión,
> que son precisamente lo que permite a otra persona o a otro agente retomar el trabajo. Se
> recomienda cambiarlo por reglas específicas (por ejemplo, ignorar solo
> `.claude/settings.local.json`). Es decisión del propietario del repositorio.

## 8. Editor

`.vscode/extensions.json` recomienda: ESLint, Prettier, Stylelint, Tailwind CSS IntelliSense,
Vitest, SQLite Viewer. `.vscode/settings.json` fija formateo al guardar y corrección de ESLint al
guardar, para que el formato no aparezca nunca en una revisión de código.
