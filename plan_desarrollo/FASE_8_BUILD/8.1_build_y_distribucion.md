# Fase 8 — Construcción y distribución

## 1. Contexto de despliegue

El destinatario es una E.S.E colombiana: equipos con **Windows**, a menudo de gama baja, red
institucional restringida, y personal de sistemas con poca disponibilidad. El plan de distribución
se ajusta a eso, no a un escenario ideal.

| Plataforma | Prioridad | Formato |
|---|:-:|---|
| Windows 10/11 x64 | **Principal** | NSIS (`.exe`) + opcionalmente MSI para despliegue por directiva de grupo |
| Linux x64 | Secundaria | AppImage + `.deb` |
| macOS | Solo si se solicita | DMG (arm64 + x64) |

## 2. Configuración de `electron-builder`

```yaml
appId: co.valuacionactivos.app
productName: Valuación de Activos
copyright: © 2026

directories:
  output: dist
  buildResources: build

files:
  - out/**/*
  - package.json
  - "!**/*.map"
  - "!**/node_modules/**/{test,__tests__,docs,example}/**"

extraResources:
  - from: recursos/plantillas
    to: plantillas
  - from: recursos/semillas
    to: semillas

asar: true
asarUnpack:
  - "**/node_modules/better-sqlite3/**"   # el binario nativo debe quedar fuera del asar

win:
  target: [{ target: nsis, arch: [x64] }]
  icon: build/icon.ico
  artifactName: ValuacionActivos-${version}-setup.${ext}

nsis:
  oneClick: false                    # el usuario elige la carpeta
  perMachine: false                  # por defecto por usuario: no exige administrador
  allowElevation: true               # ...pero permite instalar para todos si lo necesita
  allowToChangeInstallationDirectory: true
  createDesktopShortcut: true
  createStartMenuShortcut: true
  deleteAppDataOnUninstall: false    # ★ NUNCA borrar userData: contiene la base de datos
  license: build/LICENCIA.txt

linux:
  target: [AppImage, deb]
  category: Office

mac:
  target: [{ target: dmg, arch: [arm64, x64] }]
  category: public.app-category.business
```

### Dos ajustes que evitan desastres

**`deleteAppDataOnUninstall: false`.** El directorio `userData` contiene la base de datos con
ejercicios cerrados, que son evidencia contractual. Un desinstalador que la borre destruye el
producto de meses de trabajo. Se documenta además en el manual: la desinstalación no elimina los
datos, y para eliminarlos hay que hacerlo a mano y a propósito.

**`asarUnpack` de `better-sqlite3`.** Un módulo nativo no se puede cargar desde dentro del archivo
`asar`. Sin esta línea, la aplicación funciona en desarrollo y falla al arrancar instalada — el fallo
más frecuente al empaquetar Electron con SQLite (`RG-06`). Verificado por `T-A-03` desde el hito A.

## 3. Módulos nativos

```bash
npm install                 # ejecuta postinstall
# postinstall: electron-builder install-app-deps
#   → recompila better-sqlite3 contra los encabezados de Electron
```

Reglas:
1. Tras cambiar la versión de Electron, **siempre** `npm run postinstall` y regenerar el paquete.
2. CI empaqueta en cada commit (`T-A-08`): un fallo de recompilación se detecta en horas, no en
   meses.
3. Un segundo módulo nativo requiere aprobación explícita (`G-6`): cada uno multiplica este riesgo.

## 4. Versionado

**Versionado semántico**, con un matiz propio de este dominio:

| Cambio | Incremento |
|---|---|
| Corrección de interfaz o de texto | Parche |
| Función nueva sin migración de esquema | Menor |
| Migración de esquema | Menor, con nota destacada en las notas de la versión |
| **Cambio en el motor de cálculo que altere resultados** | **Mayor**, siempre |
| Cambio de major de Electron | Mayor |

La tercera fila es la regla propia: si una versión nueva calcula distinto que la anterior, los
ejercicios cerrados con la versión anterior **siguen siendo válidos** (están congelados y sellados),
pero un recálculo daría otra cifra. Ese cambio no puede pasar desapercibido en un número de parche.

Cada ejercicio guarda la versión de la aplicación con la que se calculó y con la que se cerró.

## 5. Actualizaciones

Ver [ADR-024](../DECISIONES/adr_arquitectura.md#adr-024--empaquetado-y-actualizaciones).

**v1: sin actualización automática.** Motivos:

1. La red de un hospital suele bloquear las descargas salientes; un actualizador que falla en
   silencio es peor que no tenerlo.
2. Una actualización que se instala sola durante un cálculo masivo o un cierre de ejercicio es un
   riesgo desproporcionado.
3. La instalación la controla el área de sistemas, con su propio procedimiento.

**Lo que sí se hace en v1:**
- La aplicación muestra su versión y la del esquema en el panel general y en el pie de los informes.
- Se publica un archivo `versiones.json` junto al instalador para que sistemas verifique
  manualmente.
- `electron-updater` queda preparado en el código, desactivado por configuración, para habilitarlo
  cuando el cliente lo autorice.

## 6. Firma de código (`RG-18`)

Sin firma, Windows SmartScreen muestra una advertencia y en algunos hospitales el antivirus bloquea
la ejecución. Tres opciones, en orden de preferencia:

| Opción | Coste | Efecto |
|:-:|---|---|
| 1 | Certificado EV de firma de código a nombre del contratista | Sin advertencia desde la primera instalación |
| 2 | Certificado OV estándar | Advertencia inicial que desaparece al ganar reputación |
| 3 | Sin firma | Procedimiento de instalación documentado; hash SHA-256 publicado para verificar; puede requerir excepción del antivirus |

**Decisión pendiente del cliente** (`T-H-02`). Si se elige la opción 3, el manual debe explicar el
procedimiento y la advertencia debe comunicarse al área de sistemas **antes** de la entrega, no el
día de la instalación.

Las credenciales de firma viven solo en el gestor de secretos de CI, nunca en el repositorio
(`E-3`).

## 8. Requisitos del equipo destino

| Recurso | Mínimo | Recomendado |
|---|---|---|
| Sistema operativo | Windows 10 21H2 x64 | Windows 11 |
| Procesador | Doble núcleo 2 GHz | Cuatro núcleos |
| Memoria | 8 GB | 16 GB |
| Disco | 2 GB + espacio para fotos (≈ 12 GB con 20.000 bienes) | SSD |
| Pantalla | 1366 × 768 | 1920 × 1080 |
| Periféricos | — | Escáner de código de barras USB, impresora de etiquetas |

**Disco: SSD recomendado, no exigido.** SQLite en un HDD con 20.000 bienes sigue siendo aceptable,
pero el arranque en frío de `RNF-14` (< 5 s) se midió considerando el peor caso.

## 9. Procedimiento de instalación en el hospital

1. Verificar el hash SHA-256 del instalador.
2. Instalar (por usuario o por máquina, según la política del área de sistemas).
3. Al primer arranque, elegir la ruta de datos. **La verificación de unidad de red se activa aquí**
   (`RG-10`): si se elige una ruta de red, la aplicación la rechaza y explica por qué.
4. Configurar la carpeta de respaldo externa (esta **sí** puede estar en la red).
5. Crear el usuario administrador inicial.
6. Cargar la parametrización de la entidad (paso 01) o importar la de otro hospital (`RF-01-09`).
