# Fase 7 — Seguridad

Basada en la skill `.claude/skills/electron-skill/SKILL.md` y en la lista de verificación de
seguridad de Electron.

## 1. Modelo de amenaza

La aplicación no se expone a internet (`RNF-08`). Eso descarta amenazas de red, pero deja tres
vectores reales:

| # | Vector | Escenario concreto |
|:-:|---|---|
| A-1 | **Contenido malicioso importado** | Un `.xlsx` con fórmulas o una cadena diseñada para inyección; un `.docx` de plantilla manipulado; un nombre de archivo con `../` |
| A-2 | **Dependencia comprometida** | Un paquete de npm con código malicioso ejecutándose con los privilegios del proceso main |
| A-3 | **Alteración de la evidencia contable** | Alguien con acceso al equipo modifica un ejercicio cerrado para cambiar un valor ya resuelto |

A-3 es el que distingue a este sistema. No es una app cualquiera: custodia los soportes de
resoluciones firmadas por el Gerente de una entidad pública.

## 2. Configuración obligatoria de Electron

| Ajuste | Valor | Por qué |
|---|---|---|
| `contextIsolation` | `true` | Aísla el contexto del preload del de la página |
| `nodeIntegration` | `false` | El renderer no accede a Node |
| `sandbox` | `true` | El renderer corre en el sandbox del sistema operativo |
| `webSecurity` | `true` | Nunca se desactiva, ni "temporalmente" para desarrollo |
| `allowRunningInsecureContent` | `false` | — |
| `webviewTag` | `false` | Etiqueta `<webview>` deshabilitada |
| `enableWebSQL` | `false` | API obsoleta, superficie innecesaria |

Verificados por el test automatizado de `T-A-07`, que lee el objeto de opciones. No hay excepciones
"solo mientras desarrollamos": las excepciones temporales sobreviven al proyecto.

## 3. Política de seguridad de contenido

```
default-src 'none';
script-src  'self';
style-src   'self' 'unsafe-inline';   /* CSS-in-JS lo requiere; se elimina si se prescinde de él */
img-src     'self' data: blob:;       /* fotos comprimidas en canvas */
font-src    'self';
connect-src 'self';
media-src   'self' blob:;             /* vista previa de imágenes */
object-src  'none';
frame-src   'none';
base-uri    'none';
form-action 'none';
```

Aplicada con `session.defaultSession.webRequest.onHeadersReceived`, **no** solo con la etiqueta
`<meta>`: la cabecera cubre todos los recursos, la etiqueta no.

`connect-src 'self'` sin dominios externos es la implementación técnica de `RNF-08`, y el escenario
E2E 18 (ejecución con la red bloqueada) es su verificación.

## 4. Navegación y ventanas

```ts
app.on('web-contents-created', (_, contents) => {
  contents.on('will-navigate', (e, url) => {
    if (!esOrigenPropio(url)) e.preventDefault();
  });
  contents.setWindowOpenHandler(({ url }) => {
    if (esEnlaceExternoPermitido(url)) shell.openExternal(url);   // solo https:, mailto:
    return { action: 'deny' };                                    // nunca abrir ventanas nuevas
  });
  contents.session.setPermissionRequestHandler((_, __, cb) => {
    cb(false);   // ADR-015: no hay cámara. Se deniegan TODOS los permisos
  });
});
```

`esEnlaceExternoPermitido` acepta únicamente `https:` y `mailto:`, y rechaza `file:`, `javascript:`
y cualquier otro esquema.

## 5. Validación de las entradas por IPC

La cadena de middleware de [2.3 §4](../FASE_2_ARQUITECTURA/2.3_contrato_ipc.md) es la defensa
central. Las seis prohibiciones de `2.3` §8 son reglas de seguridad, no de estilo:

| # | Prohibición | Amenaza |
|:-:|---|---|
| P-1 | Ningún canal recibe una ruta de archivo del renderer | Escape del sandbox por *path traversal* (A-1) |
| P-2 | Ningún canal recibe SQL ni nombres de tabla | Inyección |
| P-3 | Ningún canal recibe código o plantillas para evaluar | Ejecución arbitraria |
| P-4 | Nunca se devuelve al renderer una excepción con su traza | Filtración de estructura interna |
| P-5 | Nada de `sendSync` | Bloqueo del renderer |
| P-6 | Los eventos no se difunden a todas las ventanas | Fuga entre ventanas |

Sobre P-1, la regla operativa: **el diálogo de archivos lo abre siempre el proceso main**
(`dialog.showOpenDialog`). El main obtiene la ruta del sistema operativo, nunca del código no
confiable. El renderer maneja identificadores, no rutas.

## 6. Tratamiento de archivos importados (A-1)

| Riesgo | Mitigación |
|---|---|
| Nombre de archivo con `../` o caracteres de control | Se descarta el nombre recibido; el almacén genera el suyo a partir del UUID del registro |
| `.xlsx` con fórmulas maliciosas | ExcelJS lee **valores**, no evalúa fórmulas. Al exportar, los campos de texto que empiezan por `=`, `+`, `-` o `@` se neutralizan (prefijo `'`) para evitar inyección de fórmulas en el Excel del destinatario |
| Archivo enorme como denegación de servicio | Límite de tamaño configurable (por defecto 50 MB) y de filas (100.000), con mensaje claro |
| `.docx` de plantilla manipulado | Las plantillas solo se instalan desde `userData/plantillas/` por un usuario administrador; el hecho queda en bitácora |
| Zip-slip al importar un `.valz` | Toda ruta extraída se normaliza y se verifica que quede dentro del directorio destino |
| Contenido activo en imágenes | Las fotos se recodifican en el renderer con `<canvas>`, lo que descarta cualquier carga útil incrustada |

La neutralización de fórmulas al exportar merece énfasis: la aplicación genera archivos que un
contador abrirá en su Excel. Un campo de justificación que empiece por `=` se convertiría en fórmula
en su equipo.

## 7. Integridad de la evidencia contable (A-3)

> **Actualizado el 2026-09-01.** Esta sección trataba de autenticación y permisos. Tras
> [ADR-016](../DECISIONES/adr_arquitectura.md#adr-016--modelo-de-usuario-y-despliegue) la aplicación
> **no tiene inicio de sesión**: es monousuario y se instala a una persona. Ya no hay credenciales
> que proteger, y el control de acceso lo provee el propio sistema operativo.

**Lo que sí protege el sistema, y es lo que una auditoría necesita:** no impedir el acceso, sino
hacer **detectable** cualquier alteración.

| # | Medida | Contra qué |
|:-:|---|---|
| 1 | Triggers `INT-09`: un ejercicio `CERRADO` rechaza toda escritura, **también desde SQL directo** | Que alguien edite un ejercicio ya resuelto con una herramienta externa |
| 2 | Hash SHA-256 del contenido del ejercicio al cerrarlo, reverificable en cualquier momento | Que la alteración pase inadvertida |
| 3 | Bitácora completa, escrita en la misma transacción que el cambio | Que un cambio no deje rastro |
| 4 | Justificación obligatoria en los 8 campos sensibles de `ANEXO_B` §7.1 | Que un cambio sensible quede sin motivo registrado |
| 5 | Respaldo permanente al cerrar cada ejercicio | Pérdida de la evidencia |
| 6 | Cifrado de disco del sistema operativo (BitLocker), recomendado en el manual | Equipo robado o extraviado |

**Atribución sin autenticación.** Los documentos exigen decir quién certificó, valuó, avaluó y firma.
Eso se resuelve con el catálogo de `Responsable` (ADR-016): personas con perfil, cargo, tarjeta
profesional y registro R.A.A, que se seleccionan al firmar. Es **dato**, no credencial — pero queda
impreso en el documento y registrado en la bitácora, que es exactamente lo que la Resolución 193 de
2016 exige.

**Límite honesto, declarado.** Quien tenga acceso administrativo al equipo puede borrar los triggers
y reescribir la base. Ninguna aplicación local puede impedirlo. Lo que sí garantiza el sistema es que
esa manipulación **deja huella**: el hash del ejercicio cerrado ya no coincidirá.

## 9. Datos personales

La aplicación almacena nombres de funcionarios (responsables de custodia, especialistas, miembros
del Comité) y sus firmas. Son datos personales bajo la normativa colombiana de protección de datos.

| Medida | Nota |
|---|---|
| No se registran datos personales en los archivos de log | Solo en la base, donde son dato de negocio (catálogo `Responsable`) |
| Los datos no salen del equipo salvo en los entregables que el contrato exige | `RNF-08` |
| El `.valz` de exportación incluye datos personales: se advierte al exportar | Debe tratarse como documento confidencial |
| Los conjuntos de prueba con datos reales se anonimizan antes de versionarse | Fase 6 §7 |
