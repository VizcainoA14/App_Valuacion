# Fase 3.2 — Compatibilidad, transpilación y Browserslist

Responde al punto 5 del encargo: *maximizar la compatibilidad con navegadores de hasta 4 años de
antigüedad*, definiendo estrategia de transpilación, Browserslist y verificación de librerías, y
considerando la relación entre la versión de Electron (Chromium) y el frontend.

---

## 1. La tensión, planteada con honestidad

En una aplicación Electron el renderer se ejecuta en **un Chromium conocido, único y moderno**: el
que la aplicación empaqueta. En sentido estricto, la compatibilidad con navegadores antiguos es
irrelevante para el usuario final, y compilar hacia atrás solo produce paquetes más grandes y
lentos.

Sin embargo, el requisito `R-05` es explícito y hay dos razones legítimas que lo sostienen:

1. **`RF-02-01` / `RF-02-02` piden captura móvil.** Si algún día se habilita el módulo LAN de v1.5
   ([ADR-015](../DECISIONES/adr_arquitectura.md#adr-015--captura-móvil-offline-rf-02-01)), ese código
   correrá en el navegador del teléfono de un técnico de hospital — a menudo un equipo con Android
   antiguo y un WebView desactualizado. Ahí el piso sí muerde.
2. **Reversibilidad.** Escribir el renderer contra un piso conservador mantiene abierta la opción de
   desplegar la interfaz en un navegador sin reescribirla.

**Resolución: dos objetivos de compilación, no uno.** No se penaliza el escritorio para satisfacer
un requisito que solo aplica al código compartido, ni se abandona el requisito.

## 2. Definición del piso (4 años desde 2026-09)

Cuatro años atrás son **septiembre de 2022**. Las versiones estables en esa fecha:

| Navegador | Versión del piso | Fecha | Motor |
|---|:-:|---|---|
| Chrome | **105** | ago 2022 | Blink |
| Edge | **105** | sep 2022 | Blink |
| Firefox | **104** | ago 2022 | Gecko |
| Safari / iOS Safari | **15.6** | jul 2022 | WebKit |
| Samsung Internet | **18** | ago 2022 | Blink |

**Nivel de lenguaje resultante: ES2021 seguro, ES2022 verificado caso por caso.**

### Qué se puede usar

| Característica | Chrome | Firefox | Safari | ¿Permitida? |
|---|:-:|:-:|:-:|:-:|
| `??`, `?.`, `||=` | 85 | 79 | 14 | Sí |
| `Array.prototype.at()` | 92 | 90 | 15.4 | Sí |
| `Object.hasOwn()` | 93 | 92 | 15.4 | Sí |
| `structuredClone()` | 98 | 94 | 15.4 | Sí |
| Campos privados de clase (`#x`) | 74 | 90 | 14.1 | Sí |
| `Array.prototype.findLast()` | 97 | 104 | 15.4 | Sí (justo en el límite de Firefox) |
| Bloque estático de clase | 94 | 93 | 16.4 | **No** — Safari 16.4 supera el piso |
| `Array.prototype.toSorted()` | 110 | 115 | 16 | **No** |
| `Object.groupBy()` | 117 | 119 | 17.4 | **No** |
| `await` de nivel superior | 89 | 89 | 15 | Sí (Vite lo maneja) |

### CSS: aquí está el riesgo real

| Característica | Chrome | Firefox | Safari | ¿Permitida? |
|---|:-:|:-:|:-:|:-:|
| Variables CSS, Grid, Flexbox | ✓ | ✓ | ✓ | Sí |
| `:focus-visible` | 86 | 85 | 15.4 | Sí |
| `aspect-ratio`, `gap` en flex | ✓ | ✓ | 15 | Sí |
| **`:has()`** | 105 | **121** | 15.4 | **No** — Firefox 121 es de dic 2023 |
| **Anidamiento CSS nativo** | 112 | 117 | 16.5 | **No** |
| **Consultas de contenedor** | 105 | 110 | 16 | **No** |
| **`color-mix()`** | 111 | 113 | 16.2 | **No** |
| **`@property`** | 85 | 128 | 16.4 | **No** |
| `text-wrap: balance` | 114 | 121 | 17.5 | **No** (degrada bien; permitido como mejora progresiva) |

> **Consecuencia directa:** `color-mix()` y `@property` son la base del sistema de color de
> **Tailwind CSS v4**. Por eso el plan fija **Tailwind 3.4.x** ([`RG-09`](../FASE_1_ANALISIS/1.3_riesgos.md)).
> Es el hallazgo más importante de esta auditoría y la razón por la que la auditoría se hace antes
> de instalar dependencias, no después.

## 3. Configuración de Browserslist

`.browserslistrc` en la raíz, con dos entornos:

```
# Entorno por defecto y "web": el piso de 4 años (R-05).
# Aplica al código compartido y a cualquier despliegue en navegador.
[production]
chrome >= 105
edge >= 105
firefox >= 104
safari >= 15.6
ios_saf >= 15.6
samsung >= 18
not dead
not op_mini all

# Renderer de escritorio: el Chromium que Electron empaqueta.
# El valor exacto lo fija T-A-01 tras congelar la versión de Electron.
[electron]
electron >= 33.0
```

Comprobación tras cualquier cambio:

```bash
npx browserslist                        # lista efectiva del entorno por defecto
npx browserslist --env=electron
npx browserslist-lint                   # advierte de consultas contradictorias
```

`browserslist` se mantiene actualizado (`npx update-browserslist-db@latest`) como parte de
`T-A-01`; una base de datos vieja produce resultados equivocados sin avisar.

## 4. Transpilación

**No se usa Babel.** Vite compila con **esbuild** en desarrollo y en producción, y esbuild acepta
directamente objetivos de navegador. Añadir Babel duplicaría el tiempo de construcción sin aportar
nada que aquí haga falta.

`vite.config.ts` (renderer):

```ts
import { defineConfig } from 'electron-vite';
import react from '@vitejs/plugin-react';
import browserslistToEsbuild from 'browserslist-to-esbuild';

export default defineConfig({
  renderer: {
    plugins: [react()],
    build: {
      // ESCRITORIO: se compila contra el Chromium real de Electron.
      // browserslist-to-esbuild traduce .browserslistrc al objetivo de esbuild.
      target: browserslistToEsbuild(process.env.PERFIL === 'web' ? undefined : ['electron 33']),
      cssTarget: browserslistToEsbuild(),   // CSS SIEMPRE al piso conservador
      sourcemap: true,
      minify: 'esbuild',
    },
  },
});
```

Dos decisiones dentro de esa configuración:

1. **JavaScript** se compila al objetivo de Electron en el escritorio (paquete más pequeño) y al
   piso de 4 años cuando `PERFIL=web`.
2. **CSS se compila siempre al piso conservador.** El CSS es la parte que se rompe en silencio: una
   regla no soportada no lanza error, simplemente no se aplica, y el diseño se descompone sin que
   nadie se entere. El coste de mantener el CSS conservador es despreciable.

Además, PostCSS con **Autoprefixer** alimentado por el mismo `.browserslistrc`, para que los
prefijos de proveedor los decida la misma fuente de verdad.

## 5. Verificación automática (no basta con la intención)

### 5.1 `eslint-plugin-compat`

Detecta el uso de APIs de navegador no soportadas por el `.browserslistrc`. Es la red de seguridad
que impide que una API moderna entre por descuido:

```js
// eslint.config.js
import compat from 'eslint-plugin-compat';

export default [
  {
    files: ['src/renderer/**/*.{ts,tsx}', 'src/compartido/**/*.ts'],
    plugins: { compat },
    rules: { 'compat/compat': 'error' },   // error, no advertencia
  },
];
```

### 5.2 `@typescript-eslint` con `lib` restringida

`tsconfig.renderer.json` fija `"lib": ["ES2021", "DOM", "DOM.Iterable"]`. Así, usar
`Object.groupBy()` es un error de compilación, no un fallo en tiempo de ejecución en el teléfono de
un técnico.

### 5.3 Auditoría de dependencias contra el piso

Toda dependencia nueva del renderer pasa por esta comprobación **antes** de instalarse:

```bash
npm view <paquete> engines browserslist
npx are-the-types-wrong <paquete>       # empaquetado ESM/CJS correcto
```

y se registra en [3.3 Matriz de dependencias](3.3_matriz_dependencias.md) con su veredicto.

### 5.4 Auditoría manual del CSS

`eslint-plugin-compat` no cubre CSS. Se añade **stylelint** con
`stylelint-no-unsupported-browser-features`, alimentado por el mismo `.browserslistrc`. Es lo único
que detecta un `:has()` colado en una hoja de estilos.

## 6. Veredicto de compatibilidad de las librerías elegidas

| Librería | Piso propio | ¿Cumple `R-05`? | Nota |
|---|---|:-:|---|
| React 19 | ES2015+, sin APIs modernas de navegador | Sí | Verificado: no usa `Object.groupBy` ni `:has()` |
| React Router 7 (memoria) | ES2020 | Sí | El modo memoria no toca la API History |
| **Tailwind CSS v4** | Chrome 111, Safari 16.4 | **NO** | `@property`, `color-mix()`. **Descartado** |
| **Tailwind CSS 3.4** | Chrome 90, Safari 14 | Sí | **Elegido** |
| Radix UI | Chrome 90+ | Sí | Usa `:focus-visible` (Safari 15.4) |
| TanStack Table 8 / Virtual 3 / Query 5 | ES2020 | Sí | `ResizeObserver` (Safari 13.1) |
| Zustand 5 | ES2020 | Sí | `useSyncExternalStore` viene de React |
| React Hook Form 7 | ES2018 | Sí | — |
| Recharts 2 | ES2015 | Sí | SVG, sin APIs modernas |
| decimal.js | ES5 | Sí | Sin dependencias |
| Zod | ES2020 | Sí | — |
| lucide-react | ES2020 | Sí | SVG |

Las librerías que solo corren en el proceso main (ExcelJS, docxtemplater, bwip-js, better-sqlite3)
**no están sujetas a `R-05`**: se ejecutan en Node, no en un navegador. Esta distinción evita
restricciones innecesarias.

---

## 7. Qué NO se hace, y por qué

| Descartado | Motivo |
|---|---|
| `core-js` / polyfills globales | Añaden peso para soportar navegadores que el piso ya excluye. El piso está por encima de lo que `core-js` resuelve |
| Compilar a ES5 | El piso es ES2021. Compilar a ES5 duplicaría el paquete sin beneficiario |
| `@babel/preset-env` | esbuild cubre la necesidad sin duplicar la cadena de construcción |
| Bajar el piso a más de 4 años | El requisito dice "hasta 4 años". Ir más atrás tiene coste real y ningún destinatario |

---

## 8. Revisión periódica

El piso es **móvil**: "4 años" en septiembre de 2027 significará Chrome 118, no 105. Se revisa en
cada cierre de hito:

1. Recalcular la fecha del piso.
2. Actualizar `.browserslistrc`.
3. Ejecutar `npx browserslist` y `npm run lint`.
4. Comprobar si alguna restricción del §2 dejó de aplicar (por ejemplo, si `:has()` entra en el
   piso, se habilita).
5. Registrar el cambio en `/gestion_proyecto/bitacora.md`.
